# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a requester-facing TokTickIT ticketing MVP. A tester selects a temporary Development Requester, creates an IT support ticket, finds only that requester's tickets, opens a read-only detail view, and manages permitted attachments. The selected requester is a testing context only; real authentication is deferred to Lab 3.

## 2. Stakeholder Request Interpretation

The IT department needs a professional, responsive way for end users to describe a support problem, classify it, select the affected system, request a priority, attach evidence, submit the ticket, and later inspect or manage the ticket. The backend is the source of truth for Ticket Number, saved values, ownership checks, and attachment state.

## 3. Scope

### Included

- Development Requester selection and temporary requester context.
- Create Ticket with validation and generated Ticket Number.
- Categories and Related Systems loaded from PostgreSQL.
- Requester-owned My Tickets with search, filters, sorting, and pagination.
- Requester-owned read-only Ticket Detail.
- Attachment upload, metadata, active download, and soft removal.
- Zen Green UI, reusable states, responsive behavior, accessibility, automated tests, E2E tests, and evidence.

### Excluded

- Login, logout, passwords, sessions, tokens, authentication, and real role-based authorization.
- IT Staff queue, claiming, reassignment, or IT Priority workflow.
- Public Comments, Internal Notes, and Actions Taken.
- Resolving, closing, reopening, cancelling, or other post-creation status changes.
- Administration of users, roles, requesters, categories, or systems.

## 4. Functional Requirements

- FR-01: The application shall load active Development Requesters from PostgreSQL.
- FR-02: The selection screen shall clearly state that it is a Lab 2 testing mechanism, not authentication.
- FR-03: The application shall persist the selected requester context using the documented temporary mechanism.
- FR-04: The application shall display the selected requester and provide Change Requester.
- FR-05: The application shall load active Categories and Related Systems from the API.
- FR-06: The Create Ticket screen shall collect Category, Related System, Summary, Description, Requested Priority, and Attachments.
- FR-07: The backend shall validate all ticket input and generate the official Ticket Number.
- FR-08: A new Ticket shall be saved with status NEW and the selected requester relationship.
- FR-09: The UI shall show initial, loading, validation, submitting, success, and failure states.
- FR-10: The My Tickets API shall return only Tickets owned by the selected requester.
- FR-11: My Tickets shall support documented search, filters, sorting, and pagination.
- FR-12: The My Tickets UI shall show loading, empty, no-results, and failure states.
- FR-13: The Ticket Detail API shall return only a Ticket owned by the selected requester.
- FR-14: Ticket Detail shall present ticket fields as read-only.
- FR-15: The API shall accept only permitted attachment types and sizes.
- FR-16: A Ticket shall have at most five active attachments.
- FR-17: Active attachments shall expose metadata and owner-authorized download.
- FR-18: Attachment removal shall be soft removal with a required reason.
- FR-19: Removed attachments shall remain visible as metadata but not be downloadable or previewable.
- FR-20: The UI shall remain usable at desktop, tablet, and mobile widths.

## 5. Business Rules

- BR-01: Ticket Number is generated by the backend and is unique.
- BR-02: Ticket Number uses the format `TKT-YYYYMMDD-XXXXXX`, where the numeric suffix is derived from a database-generated value.
- BR-03: A new Ticket starts with Current Status NEW.
- BR-04: The selected requester is a temporary testing identity and is not authentication.
- BR-05: Only active Requesters appear in the selection screen.
- BR-06: The frontend stores the selected requester context in localStorage; the backend receives it through `X-Requester-Id`.
- BR-07: The backend validates the requester context for every requester-owned operation.
- BR-08: A requester must not receive another requester's Ticket or Attachment data.
- BR-09: Cross-requester Ticket and Attachment access returns the documented safe 404 response.
- BR-10: Summary is required, trimmed, and 5-120 characters.
- BR-11: Description is required, trimmed, and 10-4000 characters.
- BR-12: Requested Priority is one of LOW, MEDIUM, HIGH, or URGENT.
- BR-13: Category and Related System must reference active database records.
- BR-14: Submit is disabled while a create request is in progress.
- BR-15: A failed request keeps user-entered form values in the UI.
- BR-16: Allowed attachment types are JPG, JPEG, PNG, WEBP, and PDF.
- BR-17: Each attachment is at most 5 MB and a Ticket has at most five active attachments.
- BR-18: Stored filenames are generated safely; original filenames are retained as metadata.
- BR-19: Removal requires a non-empty reason of 5-500 characters and sets removedAt without deleting metadata.
- BR-20: Removed files cannot be downloaded or previewed.
- BR-21: List pages default to page 1 and page size 10; permitted page sizes are 10, 25, and 50.
- BR-22: List sorting uses a permitted field and a stable secondary sort by id descending.

## 6. UI Specification Summary

The interface uses the Zen Green system defined in `ui-spec.md`. It includes a requester selection screen, application shell, Create Ticket, My Tickets, and read-only Ticket Detail. Labels appear above controls, required fields use an asterisk plus a nearby message, buttons have visible text, busy buttons are disabled, and keyboard focus remains visible. Loading, validation, success, failure, empty, no-results, invalid-upload, active-upload, and removed-upload states are explicit.

## 7. Data Changes

The Prisma schema shall contain `RequesterUser`, `RelatedSystem`, `Ticket`, `Attachment`, and the existing `Category` model. A RequesterUser owns many Tickets, a Ticket belongs to one RequesterUser and one Category, a Ticket may use one RelatedSystem, and a Ticket has many Attachments. Ticket Number is unique. Attachment removal uses nullable `removedAt` and `removalReason`. The schema must include foreign keys, timestamps, enum values, and indexes justified by list queries.

## 8. API Contract Summary

The full request and response shapes are defined in `api-spec.md`. Requester-owned endpoints require `X-Requester-Id`. Reference data endpoints return active records. Ticket creation returns HTTP 201 and the saved Ticket. List retrieval returns items plus pagination metadata. Invalid input returns 400, missing or unauthorized resources return 404, unsupported uploads return 415, oversized uploads return 413, conflicts return 409 where applicable, and unexpected failures return safe 500 messages.

## 9. Acceptance Criteria

- AC-01: Given an active requester, when the selector loads, then that requester can be selected and continued into the application.
- AC-02: Given an inactive requester, when the selector loads, then the inactive requester is not displayed.
- AC-03: Given valid ticket data, when the requester submits, then exactly one Ticket is saved with a unique official Ticket Number.
- AC-04: Given invalid required input, when the requester submits, then field-level errors appear and the API is not called.
- AC-05: Given a backend failure during creation, when the request fails, then a safe error appears and form values remain.
- AC-06: Given Requester A creates a Ticket, when Requester A opens My Tickets, then the Ticket appears.
- AC-07: Given Requester B is selected, when My Tickets loads, then Requester A's Ticket is not returned.
- AC-08: Given a list with many Tickets, when the requester searches, filters, sorts, or changes page, then the result and metadata follow the documented contract.
- AC-09: Given an owned Ticket, when the requester opens Detail, then read-only ticket values and attachment metadata appear.
- AC-10: Given another requester's Ticket id, when the requester requests it, then Ticket data is not returned.
- AC-11: Given a permitted file under 5 MB, when it is uploaded, then active metadata is saved and the owner can download it.
- AC-12: Given an invalid type, oversized file, or sixth active file, when upload is attempted, then the upload is rejected safely.
- AC-13: Given an active attachment, when the owner removes it with a valid reason, then metadata remains and download is blocked.
- AC-14: Given a removed attachment, when any requester requests its file, then the file is not downloadable or previewable.
- AC-15: Given desktop, tablet, and mobile widths, when each screen is opened, then controls remain readable without clipping or horizontal page scrolling.
- AC-16: Given the final repository, when documented tests run from main, then all required tests pass without skips.

## 10. Definition of Done

- All approved scope is implemented and all ACs are mapped to passing tests.
- Prisma migration and repeatable seed work with PostgreSQL.
- API, UI, unit, responsive, visual, and E2E tests are present at the paths in `tests.md`.
- No required test is skipped, disabled, flaky, or unrelated.
- Success, failure, boundary, ownership, empty, no-results, and attachment states are demonstrated.
- UI follows `ui-spec.md` at desktop, tablet, and mobile sizes.
- README, `.env.example`, reviewer evidence, AI-use reflection, and screenshots are current.
- Peer review approvals and responses are recorded.
- Final integration tests pass from `main`.

## 11. Assumptions and Decisions

- `X-Requester-Id` is a temporary test context and must be replaced by real authentication in Lab 3.
- Local filesystem storage is acceptable for Lab 2 attachment demonstrations; generated runtime files stay ignored by Git.
- A Ticket remains saved if a later attachment upload fails; the UI reports the attachment failure and preserves metadata already saved.
- The API owns authoritative validation; frontend validation provides immediate feedback but does not replace backend validation.
